# Commercial v1.2 migration and release runbook

Production execution is outside this task. Keep the application release and additive
schema migration together. Booking Only is configured at 50 EGP per monthly seat;
the legacy enrollment flag remains disabled. Trial approval-start is disabled.

1. Stop admission of commercial/booking writes for the maintenance cutover. Take a
   verified SQL Server full backup with checksum and retain the previous application
   image/configuration. Restore the backup into an isolated non-production database.
2. Run `sql/V1.2-RECONCILIATION.sql` before migration and retain results. Export row IDs
   and immutable accepted terms/payment totals for comparison; do not export PHI.
3. Apply `20261105111042_CommercialContractsAndPracticeAllocations` on the restored
   database. Its SQL is additive: no Practice, Reservation, Ticket, Encounter,
   Prescription, payment or history row is deleted. Renewals join only through verified
   audit links with matching owner/product and ordered periods. Ambiguous links remain
   independent series and are recorded for review.
   If using sqlcmd, pass `-I -b` (QUOTED_IDENTIFIER ON and stop on errors), for example
   `sqlcmd -S <server> -E -I -b -d <restored-test-db> -i sql/V1.2-MIGRATION.sql`.
   Filtered indices require the SQL Server session's supported SET options. Rehearse
   the same deployment runner and options intended for the controlled release.
4. Rerun reconciliation. Original healthcare row counts, identifiers and accepted
   financial snapshots must agree. Inspect every migration exception. A practice
   without a proven currently effective old entitlement remains commercially uncovered.
   A used trial stays used; an unused trial is eligibility and creates no running period.
5. Verify grandfathered current allocations against the backup. An existing overrun
   cannot grow; the first renewal needs explicit compliant practice/reception selections.
   Unverified booking origins are flagged `OriginalEntitlementNotProven`; do not assign
   Premium grants, cancel bookings or alter medical records to clear this exception.
6. Run the existing security seeder and commercial catalog seeder through the established
   controlled initialization process. Existing permission GUIDs are unchanged; two new
   Doctor permissions are appended. Preserve the existing feature matrix/readiness.
7. Verify Doctor/Reception/Patient/Guardian authorization, exclusive UTC boundaries,
   late-worker scheduled coverage, public search/slots and transactional booking checks.
   Rehearse payment replay, trial replay, last-seat races, Outbox retry and backup restore.
8. Resume writes only after migration/security review and release signoff. Monitor
   allocation/renewal conflicts and migration issue counts without logging patient data.

Rollback before writes can use the verified backup plus the previous application/config.
After v1.2 writes, prefer roll-forward. The EF Down migration refuses a destructive
downgrade when concurrent contracts or proven commitment records exist; v1.0 cannot
represent these facts. Do not drop v1.2 data to force a rollback. Restore rehearsal must
prove the recovery point and reconcile post-backup writes through an approved procedure.

A renewal selection refers to exact allocation IDs. If a selected practice was moved,
the old contract never reclaims it. A stale selection is flagged `RenewalSelectionConflict`
and query-time coverage fails closed before any partial reconciliation. Resolve the
selection conflict through controlled review; do not change manual practice activity.

SQL Server also enforces nonoverlapping effective periods within one contract through
`TR_DoctorSubscriptions_NoPeriodOverlap` under update/hold locks. The application maps
error 51063 to a period-overlap conflict. Independent contracts are unaffected. Keep
the trigger and its EF model metadata when deploying the idempotent migration script.

The checked-in `sql/Verify-V1.2-Migration.ps1` creates a GUID-named disposable
SQL Server database, establishes the deployed foundation schema, runs reconciliation,
applies the generated v1.2 script twice, verifies the overlap trigger/migration history,
and removes only that disposable database. Run from a Release-built checkout. The
representative populated backup/restore and grandfather/ambiguous-origin rehearsal
is `CommercialV12MigrationRehearsalTests`; the script helper is the additional deployment
runner/idempotency check, not a substitute for production-data reconciliation.
