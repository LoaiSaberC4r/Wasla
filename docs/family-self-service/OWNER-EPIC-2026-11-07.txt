4.2 Implement separate operational authority:
Recommended Domain: ParentChildOperationalAuthority (or equivalent persisted exact-pair evidence derived transactionally from existing approved relationship requests). Required dimensions:
- Id; FamilyId; ParentPatientId; ChildPatientId; ParentFamilyMemberId; ChildFamilyMemberId; ParentRole Father/Mother; ApprovedRelationshipRequestId; ApprovedRequestRevision; ReviewerUserId; ApprovedAtUtc; Status Active/Revoked; RevocationAtUtc/Reason; RowVersion; CreatedOnUtc.

Reuse Family request evidence/review infrastructure where possible; add a versioned operational request only if necessary to avoid changing semantics of 3/4.
- Revocation/history and current revision checks ensure old proof cannot reauthorize new operations after evidence modification, restriction applicable to operation, family change, archived/revoked membership, or role change. No implicit family transfer.
- If using existing FamilyRelationshipRequest for operational proof, preserve enum numeric values 1–4. New enum values must append, and older clients must not misinterpret them. Prefer provenance record that points to reviewed request with exact pair.

4.3 Build explicit authorization service:
`IDependentAccessPolicy.AuthorizeAsync(DependentAccessOperation operation, Guid childPatientId, CancellationToken)`

- Distinguish `OperationalAuthority` from `MedicalAuthority`. For clinical reads use existing IFamilyMedicalAccessPolicy.ScopeAsync rather than reimplementing or weakening it. For new medical writes, implement independent WRITE check in same signed policy context, NOT infer from read scope alone.
- Permission checks at endpoint AND inside handler for direct MediatR dispatch.
- Reauthorize immediately before returning sensitive file bytes and at durable mutation commit boundaries; no stale in-memory rights.
- Current family membership, role and evidence must be revalidated; failure returns indistinguishable 404 for unrelated subjects where appropriate, secure reason codes only to current legitimate actor.

- Supported new document types only PDFs and JPEG/PNG by default; use a dedicated validated `HistoricalDocuments` allowlist and the existing BuildingBlock media validator. GIF/MP4 remain allowed in other existing media features if configured; they should not automatically be allowed for sensitive historical documents. Additional formats require explicit validation design.
- Check bounded file size/count/total quotas by configuration; suggested initial default = 10 MiB per file (align existing MediaStorage), max file count = 5 per document, all adjustable within hard absolute application safety caps. Do not infer unlimited storage. Enforce server HTTP request size as well as streamed file size; don't buffer huge contents in RAM.
- MIME by content signature, extension checks, filename sanitize, active content rejection, decompression and PDF safety policies, explicit real scanner. Use temporary quarantine until successful scan; scanner ERROR or absent when configured required => fail closed, do NOT mark Available.
- `IMalwareScanner` currently has a default NoOp fallback; install/configure real scanner adapter behind the same interface (service can be provisioned outside process). Verify quarantined temporary media cannot be downloaded.

Successful download requires fresh scoped authorization, matching subject/version/attachment, active status, exact original size/hash where supported, metadata audit persisted; send `Cache-Control: no-store`, `X-Content-Type-Options: nosniff`, safe attachment name and content disposition, disable unsafe inline script preview. - Upload storage and DB references consistency: use prevalidation/quarantine staging, DB transaction for metadata/history/idempotency/outbox, commit-aware media compensation (do not delete retained blob on ambiguous commit), orphan-file reconciliation/metrics; document worker/repair procedure and test storage failure & uncertain SQL commit.
